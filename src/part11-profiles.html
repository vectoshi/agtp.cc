Binding Profiles

A binding profile is the normative mapping between an external standard and AGTP. Profiles are how AGTP stays small: the semantics of tasks, tools, interfaces, policies, API calls and registries remain upstream-authoritative, and each profile states only which AGTP objects an upstream object or event produces, which upstream identifiers are preserved, and where AGTP identifiers travel inside the upstream protocol. The profile identifiers used in capabilities documents and observation records are registered in Appendix F.

The Profile Contract

Every profile, including those defined in this document and those registered later, MUST specify the following:

  1. the values of sourceProtocol and sourceVersion, and the members of sourceRefs that observation records preserve, with a statement of which upstream ordering semantics are preserved;
  2. which AGTP objects the profile creates—Observation Records, Artifacts, Capability Descriptors, Learning Signals, Receipts, Anchor Commitments—and from which upstream objects or events;
  3. how actor and subject DIDs are obtained, including the gateway identity rule when the upstream protocol lacks DIDs;
  4. how the interaction identifier is derived and how the provenance URI's artifacts are chosen;
  5. the separation between transport or execution outcomes (observations) and evaluative judgments (signals), and the issuance points the profile supports;
  6. the redaction and hashing strategy for payloads that may be private, expressed in terms of the privacy classes of section 5.7; and
  7. where AGTP identifiers are carried inside the upstream protocol, using the reserved keys below and nothing that the upstream protocol reserves for itself.

DID and Verifiable Credentials (Baseline)

Profile identifier: did-vc/2.1. This profile is the substrate on which every other profile depends and is not optional. It consists of the identifier requirements of section 3, the credential family and representations of section 4, and the cryptographic suite of section 10. In summary, an implementation of this profile:

  • identifies every participant by a resolvable DID and discovers services through DID Documents;
  • expresses every portable trust claim as a Verifiable Credential 2.0 with the AGTP context and one AGTP type;
  • secures documents with Data Integrity proofs, baseline eddsa-rdfc-2022, and verifies them against assertionMethod keys;
  • checks Bitstring Status List or Space status entries before use and fails closed on unresolvable DIDs, unsupported cryptosuites and unretrievable status;
  • computes signalHash, manifestHash and contentHash by the procedure of section 10.2.

Other profiles MAY start from non-credential records, but any claim that crosses an organisational boundary as evidence of trust SHOULD be upgraded to an AGTP credential before it does.

Model Context Protocol

Profile identifiers: mcp/2025-11-25 and mcp/2025-06-18, corresponding to the MCP specification revisions [MCP]. MCP defines how a client discovers and invokes a server's tools, resources and prompts over JSON-RPC 2.0; it says nothing about whether the results were any good. This profile makes MCP activity first-class evidence in AGTP without changing MCP semantics.

  1.   5. Where MCP's authorization framework is used, the resource server's identity SHOULD be bound to its DID through alsoKnownAs so that the OAuth resource and the AGTP subject are verifiably the same party.

Agentic Resource Discovery

Profile identifier: ard/0.91. The normative content of this profile is section 7. In the terms of the profile contract: sourceProtocol is ard; sourceRefs preserves the entry identifier, the registry source and the search score; the profile creates Capability Descriptors (from entries the publisher controls) and Observation Records (for searches and verification outcomes); the actor is the searching agent and the subject is the entry's agtp:did; discovery events are observations and never signals; entries are public by construction and carry no private payloads; and AGTP identifiers travel in the entry under the agtp prefix.

Open Knowledge Format

Profile identifier: okf/0.2. The normative content of this profile is section 8. In the terms of the profile contract: sourceProtocol is okf and sourceVersion is the bundle's okf_version; sourceRefs preserves the bundle CID, the concept path and, where applicable, the git commit; the profile creates Artifacts (bundles, concepts, receipts), Observation Records (generation, usage, reads), Capability Descriptors (attested computations) and Learning Signals (verification events, attester verdicts); actors are obtained from the DID forms of OKF actor identifiers; the interaction identifier for an attestation is derived from the computation's CID and parameters; verification events and attester verdicts are the issuance points; bodies MAY be private with concept CIDs still bound in provenance; and AGTP identifiers travel in the agtp frontmatter mapping.

Profile identifier: a2a/1.0, corresponding to A2A 1.0 [A2A]; earlier revisions are identified by their own version. A2A provides task lifecycle, messaging, artifact exchange and capability discovery between agents. The correct integration is not to collapse A2A into AGTP but to make A2A interactions emit AGTP objects.

A2UI

Profile identifiers: a2ui/0.8 (production baseline) and a2ui/0.9 (draft) [A2UI]. A2UI is the human-facing surface where much of the highest-value feedback originates. This profile makes UI interactions and human judgments portable without defining UI semantics.

  • A UI session or context is an Interaction, bound to the same interaction identifier as the A2A, MCP or model-API activity it presents wherever that identifier is available.
  • UI events are Observation Records (UIEventRecord) with event identifiers, order and timestamps preserved in sourceRefs; rendered snapshots, prompts and outputs are Artifacts at the privacy class Space policy assigns.
  • Only evaluative judgments—ratings, preferences, corrections, approvals and rejections, rubric scores—become Learning Signals. Telemetry (clicks, dwell, scroll) never does. Human-issued signals SHOULD carry issuerRelation and MAY carry confidence; the issuer is the human's DID or a gateway identity with a Delegation credential.
  • Evidence gathered in the interface—screenshots, annotations, correction diffs—becomes Artifacts referenced from provenance. For sensitive interfaces implementations SHOULD distil ephemeral UI observations into a persistent summary signal with a commitment.
  • Mappings MUST be version-tagged; v0.8 and v0.9 fields MUST NOT be mixed in one record without a translation layer.

AGENTS.md and Agent Skills

Profile identifier: agents-skills/1. AGENTS.md [AGENTS-MD] expresses repository or workspace policy for coding agents in free-form Markdown, with nearest-file precedence. Agent Skills [AGENT-SKILLS] package a capability as a directory with a SKILL.md whose YAML frontmatter carries name, description and optional license, compatibility, metadata and allowed-tools. Together they are the intent layer: what an agent may do and what it says it can do.

  • An AGENTS.md file in force during an interaction is an Artifact (role policy) referenced from the observation record's policyRefs. Which file applied, under nearest-file precedence, is recorded, not inferred. An AGENTS.md MAY be exchanged across organisational boundaries as a PolicyAssertion credential binding its CID.
  • A skill is a Capability with interfaceType agent-skill. The descriptor's name and description come from the frontmatter; constraints carries allowed-tools, compatibility and license; sourceArtifacts carries the CID of SKILL.md and of the skill directory; contentHash changes whenever either changes.
  • Skill authors MAY place agtp-owner (a DID), agtp-capability (the capability URI or ARD identifier) and agtp-space in the frontmatter metadata map, whose values are strings as Agent Skills requires.
  • Policy and capability MUST NOT be flattened into one another: an AGENTS.md constraint is a policyRef, not a capability, and instruction text in a SKILL.md body is execution guidance, not a declaration.
  • Signals about a skill are issued against its capability URI, and observation records reference the descriptor contentHash used at execution time, so that a Space can compare declared constraints with observed behaviour version by version.

OKF attested computations reference skills through executor.resource; when they do, the skill's capability identifier and the computation's capability identifier SHOULD be linked through sourceArtifacts so that signals on either inform the other.

Typed HTTPS API Operations

Profile identifier: https-api/1. This profile maps existing typed HTTPS request/response operations. It does not create an endpoint or grant and is distinct from http/1.1, which describes AGTP feedback delivery. Its namespace is https://schema.agtp.org/profiles/https-api#.

  • A Capability Descriptor has interfaceType: api-tool and an interface containing protocol: https, the actual upstream API contract version, fixed HTTPS url, actual method, schemaHash and schemaPayload. bindings entries carry the same fields. An API contract identifier such as gos.account.identity-trust.v1 is not an HTTP transport version or an AGTP feedback version. The actual owner codecs and endpoint remain authoritative.
  • A mapped Observation Record uses sourceProtocol: https and sourceVersion equal to that upstream contract version. Its sourceRefs preserve the exact method, endpoint, original response/request correlation identifiers, status and upstream ordering. Request and response bodies become Artifacts under the selected privacy policy; the descriptor and exact schema payload become source/config artifacts. Neither the API endpoint nor an API key is a DID.
  • The actor and capability owner DIDs come from established identity mappings. Where the API exposes only a local Account/key identifier, the observer uses its explicitly configured gateway DID and preserves the delegated actor only through authorized source evidence or an actual Delegation credential. A string Account identifier MUST NOT be turned into a DID by convention. The observation subject is the capability URI unless the actual API supplies a specific assessed-subject URI; in that case the original subject URI is preserved and the invoked capability remains in capabilityRefs. Feedback about the provider remains a separate subject choice.
  • When a response exposes an actual interaction URI, it is preserved unchanged, with its documented response pointer declared in interface.correlation.responseUri. Otherwise interface.correlation.requestIdHeader names an actual server-generated correlation header. The interaction is the ni:///sha-256; URI, with an unpadded base64url digest, of the JCS UTF-8 array [interface.url, interface.method, exactHeaderValue]. The same tuple and original header value are retained in sourceRefs. This derives an AGTP exchange identity, not a new server Run or payment receipt. A missing required correlation identifier makes invocation-provenance qualification unavailable; it MUST NOT be invented. Provenance binds actual input/output artifacts and the descriptor used for that exchange.
  • HTTP outcomes, errors, timeouts, latency, usage and quote/preflight advice are observations, not Learning Signals. A subsequent explicit human/evaluator judgment may issue a signal with the declared Space dimensions and that bound provenance. A domain Rating is not automatically a judgment about the API provider. No grant, hold, settlement or receipt is inferred from a successful read.
  • Authentication material, private keys, cookies and credentials MUST NOT be published in artifacts, comments or observation claims. Raw bodies and local principal references remain private, redacted or committed-only as policy requires; schemas contain no instance data. A replay verifier without body access reports that limitation. Failed, absent and unavailable fields MUST NOT be replaced by zero or a successful result.
  • The API's original request/response schemas and its reserved fields remain unchanged. AGTP context travels in the mapped Observation Record and in an existing API metadata location only when that upstream API actually defines one. Producers MUST NOT inject AGTP parameters, a caller-selected authoritative Account or an invented metadata header into a strict API contract.

The supported issuance points are declaration of the actual API interface, observation of a correlated exchange and an explicit subsequent judgment. Producers state which they implement. This profile uses the shared schema-payload convention without claiming a gOS Registry invocation. Existing MCP operations retain their normative MCP binding and actual tool/server/version locators.

Exact Schema Payload Bytes

Encoding identifier: jcs-schema-payload/1; hashing identifier: jcs-schema-payload-1+sha2-256. The payload is exactly an object with required inputSchema and optional outputSchema, each a materialized JSON Schema object, and no other top-level members. A missing output schema remains missing. This version does not turn an unresolved schema URI into a materialized schema.

Producers MUST encode that object with the JSON Canonicalization Scheme, RFC 8785 [RFC8785], as UTF-8 with no BOM, trailing line feed or other added bytes. JSON strings and property names MUST contain well-formed Unicode; Unicode normalization MUST NOT be applied. Numbers have the finite IEEE-754 semantics required by JCS. Duplicate members, nonfinite numbers, executable conversions and non-JSON object graphs MUST be rejected. This isolated schema-metadata encoding MUST NOT change an upstream monetary, evidence, Run, outcome or signature encoding.

schemaHash is the multibase base64url encoding (prefix u, no padding) of the SHA2-256 multihash of those exact bytes. schemaPayload is an object with encoding: jcs-schema-payload/1 and uri locating those immutable public bytes. A verifier MUST check the raw bytes against both JCS and schemaHash, then check that the descriptor's advertised schema objects agree with the payload. It MUST NOT re-encode a noncanonical response and then accept it as the original payload. A URI-valued advertised schema is qualified by this convention only when it resolves to the corresponding member of the exact pinned payload.

The existing credential owner MAY derive this public leaf from an immutable descriptor's already-public schema objects. It MUST preserve retrieval for historical versions and MUST NOT use a current/floating publication or descriptor hash inside the payload. Publishing these schema bytes does not authorize disclosure of private implementation code or user data. Schema hash equality does not prove all host semantic refinements, current admission or source authority.

Existing HTTP and MCP descriptors MAY adopt this explicit schema-payload convention while retaining their actual protocols and locators. Such adoption MUST declare schemaPayload.encoding. This is a new versioned encoding convention; it does not reinterpret historical schemaHash values whose serialization was not declared.

Identity, Provenance and Issuance

  • The Registry's existing evaluator binding carries the module DID and immutable descriptor reference. AGTP fields MUST NOT be injected into strict upstream argument bags or Run bodies. The mapped Observation Record carries the Space, capability content hash, interaction and provenance identifiers; its sourceRefs preserve their link to the existing Registry/Work evidence.
  • The interaction identifier is the actual producer Run URI when a retained Run exists. Parent/root Work and invocation identifiers remain separate references. A local resource URI or Run identifier MUST NOT be treated as an AGTP DID or as an AGTP provenance URI. Provenance uses the existing section 3.3 form and binds the actual retained input/output, declaration and outcome artifacts.
  • actor uses an upstream DID only when the existing identity owner establishes that mapping. Otherwise an explicitly configured gateway DID is used and the original upstream principal is retained only as authorized source evidence. The evaluator DID, native signing principal, atom/version, Run and feedback subject MUST remain distinct. A missing native signer_did MUST NOT be fabricated. The execution observation subject is the invoked capability URI; an output Review preserves its own Dataset subject and does not replace that execution subject.
  • Original Run/outcome bytes, native date encoding, mutation revisions and attestations remain unchanged artifacts. A completion timestamp MAY be mapped from the typed successful producer Run when actually present; it MUST NOT be invented from an outcome digest, a root Run still in progress, or read time. Native Run schema1's default JSON date representation uses reference-epoch seconds from 2001, not Unix seconds; mapping uses the upstream typed date codec. A native P256 attestation is not an AGTP Data Integrity proof.
  • Execution success, a process exit code, latency and a raw computation result are observations. A domain Review/Rating MAY be retained as an output artifact, preserving its actual subject, units, policy and unavailable state. It is not automatically feedback about the evaluator. A Learning Signal requires a separate explicit evaluative judgment, declared Space dimensions and bound provenance. No Receipt or aggregate is synthesized from a successful local call.
  • Raw, redacted and committed-only evidence follow the existing privacy classes. Public schemas contain no input values or private trace bodies. Native input/Run/outcome records MAY remain under their existing disclosure authority, with their CIDs bound by provenance. A verifier without that authority MUST report the resulting replay limitation rather than infer evidence access.

This profile's supported issuance points are capability declaration, observation of an actual retained invocation, and an explicit subsequent evaluative judgment. A producer MUST state which it supports. Registered identity, DID resolution, credential proof/status, interface qualification, current runtime admission and actual product availability MUST NOT be collapsed into one verified flag. Agent Skills and OKF profiles remain applicable only to their actual upstream packages and concepts.

ERC-8004 Trustless Agents

Profile identifier: erc8004/1. ERC-8004 [ERC-8004] defines three on-chain registries: an identity registry that mints an agent identifier bound to an off-chain registration file, a reputation registry that records feedback entries pointing at off-chain feedback files, and a validation registry that records validation requests and responses by hash. This profile lets AGTP use those registries for discovery and anchoring while keeping signals, manifests and traces off-chain, portable and chain-neutral.
